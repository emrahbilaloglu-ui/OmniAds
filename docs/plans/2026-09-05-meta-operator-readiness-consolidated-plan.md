## Corrections to the previous plan

1. **Wire the decisions before broadening execution.** An exact payload schema is not a budget-sizing or bid policy. Each producer must specify the mechanism, eligibility, exact proposed change and why that amount follows from existing profile/configuration. Never parse recommendation prose, invent universal percentages or promote an uncertain classification to fill the screen.
2. **Separate advice, operator permission and unattended permission.** An economic observation can remain useful while its execution is withheld. Explicit manual action has its own origin; it must not masquerade as an engine-authorized action. A scheduler must not fabricate an explicit manual confirmation.
3. **Automation OFF must allow deliberate manual work.** It stops unattended dispatch. The existing emergency stop stops all writes. Preserve release, identity, permission and read-back checks in both paths; do not add a second stop system.
4. **Treat configuration as a real deliverable.** Missing business control rows, unread readiness and conflicting readiness-tier checks cannot be solved by exposing UI switches. Use an idempotent default-disabled initialization and one consistent effective-mode calculation. Preserve existing explicit stops.
5. **Keep units and action meaning exact.** Commercial target ROAS and the provider's ROAS bidding control are different. Monetary changes carry currency/exponent/minor units; ROAS carries a dimensionless ratio with the provider's documented encoding. `scale` does not universally mean `resume`; an active winner, a paused candidate and a Test promotion are different actions.
6. **Complete the daily operating loop.** Include review, edit, approve/reject, defer with revisit time, execution, reconciliation, history and actionable notifications. A green API call or a recorded “done” is not verified execution.
7. **Keep blocked information visible.** “No change needed” is valid only when evaluation completed. Missing/stale inputs must appear in a distinct resolution state, not a benign empty state. Add loading, refreshing, error and no-account states to acceptance.
8. **Bound validation without weakening it.** Do not replay all historical research or keep tuning against the same held-out period. Missing historical evidence stays unknown. Separate engineering correctness, decision quality and causal business impact.
9. **ROAS-first economics.** Use the configured target ROAS as commercial intent. Compute `AOV = Shopify revenue / qualifying orders`; where an absolute spend/CPA benchmark is actually needed, compute `derived CPA = AOV / target ROAS`. Reuse the existing Shopify ledger/warehouse readers, with explicit business/store, currency, revenue definition and window. An observed Shopify AOV must not be mislabeled as an operator assumption. Persist its source and the derivation in the existing profile/evidence contract; update the relevant ADR/validators/tests together. Optional manual CPA/AOV fields may remain compatible, but their absence must never cause a “configure CPA/AOV” task. If usable Shopify data is unavailable, diagnose that data connection and withhold only calculations that actually need it; continue valid ROAS-based assessment. Only a genuinely absent ROAS target, such as IwaTR's current record, calls for target entry.
   - The normal ROAS-first path must reach both `account-decision-profile.ts:257` / `spend-unit-resolver.ts:88` and native Ad calibration/profile production, persistence and validation (`ad-account-decision-profile.ts:580`). Updating only `metaLossBudgetMaturity` in `lib/meta/commercial-targets.ts:198` leaves these authoritative consumers unchanged. Use an explicit observed-Shopify source/basis, update formula validation and evidence provenance together, and remove the corresponding “set CPA/AOV” resolution copy in `commercial-anchor.ts:123`.
   - Preserve the observed order count, cutoff and revenue definition. The ledger's AOV uses revenue while the warehouse overview uses gross revenue; do not silently alternate between them. A store-wide Shopify AOV supplies a derived operating benchmark; it is not proof of identical Meta-attributed purchase value or achieved ROAS. A positive derived value alone does not upgrade evidence confidence or authorize an action. This requires no additional user target.
